# Source Priority 规则草案（成员 C · 第三周 §7 / §8.4）

> 状态：**草案，待实测校准**。维护人：成员 C。依据：指南 §8.4 Source priority、§7.5 多来源检索实验。

## 1. 背景与目标

多来源接入后（用户手册 PDF + 开发者指南 HTML），同一问题可能被多个来源命中，
且不同来源对同一内容可能给出不一致说法。需要一条「可信度排序」规则，让生成侧
在冲突时知道优先采信谁，而不是随机取一、或掩盖分歧。

本草案只定「来源优先级」的**默认序 + 接线方式**，具体序需用 §7.5 的 A/B/C/D 四类
场景实测校准后才定版（第三周产出草案，第四周随评测定版）。

## 2. 草案默认序

指南 §8.4 给出的通用序：

```
API 参考 > 开发者指南 > 用户手册 > FAQ > 非官方资料
```

映射到本项目当前已知来源（`configs/experiments/*.yaml` 的 `sources[].id`）：

| 优先级 | source_id | 文档类别 | 说明 |
|---|---|---|---|
| 高 | `zrdds_dev_guide` | 开发者指南 | HTML / Doxygen，含 API 签名、参数、继承关系（v2.4） |
| 低 | `user_manual` | 用户手册 | PDF，面向使用者的流程/配置说明（v2.0） |
| （预留） | `api_reference` | API 参考 | 若 A 后续单独拆出 API Reference 源，置于最前 |
| （预留） | `faq` | FAQ | 非权威，置于用户手册之后 |

> 当前 `source_priority` 在 config 里保持空 `[]`：因为 `zrdds_dev_guide` 尚未注册
> （A 的 HTML 接入未完）。A 接入后按上表填 `[zrdds_dev_guide, user_manual]`，
> 生成侧即自动注入优先级话术。

## 3. 接线方式

1. **配置**：`retrieval.source_priority`（高→低的 source_id 列表），空 = 不分先后。
   - 归属在 `retrieval` 区块是既定 schema（README `configs/experiments/README.md`），
     生成侧按此字段读取，不另起新字段。
2. **注入 Prompt**：`generation/prompts/v2.py` 把列表渲染成一句话术，追加进 system：
   > 来源优先级（高→低）：开发者指南 > 用户手册。当不同来源说法冲突时，优先采信
   > 高优先级来源；若高优先级来源无相关内容，再参考低优先级来源并说明所用来源。
3. **来源标签**：`generation/context_builder.py` 在每个片段来源行追加文档类别标签
   （`source_id → SOURCE_CATEGORY`），让 LLM 能把优先级话术映射到具体片段。
   `SOURCE_CATEGORY` 与优先级标签共用 `generation/source_labels.py` 单一事实源。

## 4. 冲突披露话术（§8.4 Conflict disclosure，提前至本周）

Prompt v2 规则 5：

> 若不同来源对同一内容给出不一致说法，必须明确指出各来源分别说了什么并标注冲突，
> 不得只取其一或掩盖分歧。

与 v1 规则 4（版本差异披露）的关系：规则 4 针对**同一来源内/跨版本的版本差异**，
规则 5 针对**不同来源之间的分歧**（可能同版本，也可能跨版本）。两者可叠加：
「用户手册（v2.0）说 X，开发者指南（v2.4）说 Y，存在来源与版本双重冲突」。

## 5. 实测校准方法（§7.5 四类场景）

| 场景 | 示例问题 | 期望行为 | 校准点 |
|---|---|---|---|
| A 单一来源 | 产品如何安装？ | 只用用户手册 | 优先级不干预（只有一源） |
| B HTML 更适合 | `create_datawriter()` 的参数？ | 用开发者指南 | 开发者指南被命中时是否被正确采信 |
| C 多来源联合 | 手册的连接功能在 Java SDK 如何实现？ | 联合两源 | 联合时是否各取所长、不丢来源 |
| D 冲突/版本 | v2.4 的 API 是否仍用旧参数？ | 区分版本+来源，披露冲突 | 核心：冲突时是否按优先级采信并披露 |

校准产出：用 §7.5 D 场景构造 ≥10 个「混版本/来源冲突」样本（见
`evaluation/datasets/error_cases.jsonl`），人工核对生成是否披露冲突、是否按优先级采信，
据此微调默认序或话术措辞。

## 6. 遗留 / 开放问题

1. **与 B 的检索侧优先级是否统一**：`retrieval.source_priority` 字段是否也用于
   B 的检索排序/过滤，还是仅生成侧采信用？需与 B 对齐（避免「检索时排掉低优先级、
   生成时又需要它做冲突披露」的矛盾）。
2. **错来源处置**：当问题应由开发者指南回答、却只命中用户手册时（§7.5 错来源类），
   期望行为是「拒答 + 提示参考开发者指南」，还是「按手册可答部分回答 + 标注局限」？
   见 `error_cases.jsonl` 的 `wrong_source` 类，需与 E 对齐前端文案。
3. **弱证据阈值**：低分片段是否仍参与优先级判定，沿用第二周 citation 会签遗留的
   score 阈值问题（建议 0.5 起）。
