## 2.2 项目背景

### 2.2.1 产品与知识源背景

ZRDDS（臻融数据分发服务）是基于 DDS 规范的分布式实时数据分发中间件，使用者以嵌入式与工业软件方向的 C/C++、Java 开发者为主。其技术资料具备三个典型特征：

1. **体量大、结构深**：《ZRDDS用户手册.pdf》295 页原生文本型 PDF，内嵌书签 405 条、最深 5 级，层级为 11 个 PART → 27 章 → 127 个三级节 → 145 个四级节 → 95 个五级节。
2. **形态异构**：除 PDF 手册外，另有 ZRDDS v2.4.0 Doxygen HTML 开发指南（436 页文档，含 API 参考、FAQ、示例与类索引），二者对同一能力（如 QoS 策略、`create_datawriter()`）的表述位置与详细程度不同。
3. **开发者问题的"高精度 token"特征**：真实提问大量包含精确标识符——`DomainParticipant`、`create_datawriter()`、`HistoryQosPolicy`、`v2.4`、错误码等。这类 token 对语义向量检索不友好，对词面检索友好。

### 2.2.2 现有查文档方式的问题

| 现有方式 | 具体问题 | 后果 |
|---|---|---|
| 人工翻阅 PDF 手册 | 295 页全量检索只能靠 PDF 阅读器关键字，命中后仍需人工判断章节归属 | 单次定位耗时数分钟，定位结果不可复用 |
| 通用大模型直接作答 | 模型未见过 ZRDDS 私有 API 与错误码，倾向"合理编造"不存在的 API、参数、错误码 | 开发者按错误答案改代码，**错误被放大且难以察觉** |
| 普通全文检索 | 只能定位到"页码"，不能回答"怎么做"，且无版本区分 | 无法支撑调试类问答 |
| 跨资料人工比对 | PDF 与 HTML 两套资料需分别查、人工比对版本差异 | 版本混用风险（如把 v2.3 的接口当 v2.4 使用） |

**核心矛盾**：通用 LLM 的"流畅生成能力"与工程文档问答要求的"事实可核验"之间存在根本张力。项目要解决的不是"LLM 够不够强"，而是**如何让回答有据可查、错可控制**。

### 2.2.3 项目定位与总目标

**总目标**：构建面向 ZRDDS 开发调试场景的产品知识库与问答系统。第一阶段以《ZRDDS用户手册.pdf》为唯一知识源，交付一个**可运行、可调试、可评价**的最小 RAG 问答系统；第二阶段接入 HTML 开发指南等其他来源，形成统一多来源知识库，并完成问答、引用、可信度控制与系统评测。

**技术主线（贯穿全项目的最高约束）**：

```text
正确知识 → 正确检索 → 有依据的回答
```

**技术路线**：

```text
第一阶段  PDF → 解析/清洗 → Chunk/Node → Embedding → Vector Index → Retrieval → LLM → Citation
第二阶段  多来源独立解析 → 统一 Node/Metadata → Hybrid Retrieval/Reranker → RAG → Citation/Evaluation
```

**开发顺序（禁止倒置）**：① PDF Parsing → ② Chunking → ③ Retrieval → ④ LLM → ⑤ 问题集 → ⑥ Evaluation → ⑦ HTML → ⑧ Hybrid/Reranker → ⑨ 产品化。项目最大风险链路是 `PDF 没解析好 → Chunk 不合理 → 检索错误 → LLM 得到错误 Context → 答案看似合理实则错误`，因此需求优先级必须严格服从该顺序。

## 2.3 干系人与用户角色

| 角色 | 典型身份 | 核心诉求 | 对系统的硬性要求 |
|---|---|---|---|
| **主要用户：ZRDDS 应用开发者** | C/C++、Java 中间件开发者 | 快速确认 API 用法、配置项含义、错误码成因、操作步骤 | 答案正确、**能指到"第 X 页 第 Y 节"**、不确定时宁可拒答 |
| **次要用户：现场调试/技术支持** | 部署与排障工程师 | 依据日志与错误现象定位问题、跨资料联合查询 | 支持跨来源（手册＋开发指南）联合检索；版本可区分 |
| **次要用户：文档维护者** | 产品文档工程师 | 收集"文档未覆盖/表述不清"的问题，反向改进文档 | 拒答与低置信案例可统计、可导出 |
| **项目内部干系人** | 5 人开发团队（知识工程/检索/生成与可靠性/集成与实验平台/前端与质量） | 并行开发不互相阻塞 | 目录 Owner 制、产物交接而非口头传数据、配置驱动实验 |
| **验收方** | 课程教师/答辩评委 | 判断"是否真的解决了问题"而非"是否用了某个框架" | 可复现的三行命令、可比较的指标证据链、诚实的局限说明 |

> **需求启示**：用户的第一诉求不是"回答得多"，而是"**回答得可核验**"。这直接决定了引文（Citation）与拒答（Abstention）在本项目中是**核心功能需求**，而非可选增强项。

## 2.4 典型业务场景（用例）

场景设计参照指南 §6.1（开发者问题分类）与 §7.5（多来源检索四类场景），并按"知识来源"维度归并。

| UC-2 | **产品配置** | 如何配置 QoS 策略？某参数默认值与取值范围？ | 命中配置节，给出参数表 | 表格保真、章节定位 |
| UC-3 | **错误码与异常排查** | E1003 是什么？为什么连接失败？ | 命中错误码/日志章节；若语料无该码则明确拒答 | 精确 token 检索、拒答判定 |
| UC-4 | **开发调试流程** | 如何用交互式调试日志定位问题？日志级别怎么设？ | 命中调试日志章，给出操作步骤 | 操作流程类分块完整性 |
| UC-5 | **代码理解** | 这段代码哪里有问题？ | 引用相关示例与约束说明 | 代码块原子性 |
| UC-6 | **单一来源即可回答** | 产品如何安装？ | 命中用户手册 | 单来源基础检索 |
| UC-7 | **HTML 更适合回答** | `create_datawriter()` 的参数是什么？ | 命中开发指南 API 页，引用给 URL | 跨来源路由、URL 引用 |
| UC-8 | **多来源联合** | 用户手册里的设备连接功能在 Java SDK 中如何实现？ | 同时检索手册＋开发指南 | Hybrid 检索、多来源上下文组装 |
| UC-9 | **版本/冲突问题** | v2.4 的 API 是否仍使用旧参数？ | 区分版本与来源，显式披露冲突 | 版本元数据、冲突披露话术 |
| UC-10 | **知识库不存在的信息** | 文档未提及的某个能力是否存在？ | 明确回答"当前知识库无法确认"，并给出可参考方向 | 拒答机制、弱证据信号 |

**场景对需求的牵引**：UC-9/UC-10 是本项目区别于"通用聊天机器人"的关键——它们要求系统**具备说"不知道"的能力**，并要求**冲突必须显式披露而非静默选一**。

## 2.9 范围边界与明确不做

**本项目明确不做**（避免"把一个月耗在框架选型上"）：

| 不做项 | 理由 |
|---|---|
| Agent、GraphRAG、多智能体、复杂工作流 | 当前阶段最大风险不是 LLM 不够强，而是知识工程与检索不可靠；先保证 `正确知识 → 正确检索 → 有依据的回答` |
| 固定尺寸分块作为研究主线 | 手册结构清晰，固定尺寸分块无研究价值（可作 sanity baseline 对照） |
| OpenAI 兼容门面 / 开源 Chat UI 改造 | 经用户决策裁剪，前端走自研轻量路线，省下时间转投测试集与回归 |
| 前端界面重度美化 | 首版只做问答、来源、状态、反馈；**但 Citation（页码 + 章节）展示是硬性要求，不可省** |
| 把 LlamaIndex 当作"自动生成好知识库"的黑盒 | 框架只承担编排（Document/Node/Parser/Index/Retriever/QueryEngine/Evaluation）；产品文档结构理解、知识单元定义、Metadata Schema、来源可信度、版本冲突处理、拒答边界、问题集设计、指标与通过标准**必须由项目自己决定** |

## 2.10 约束与假设

**约束**

1. **资源**：5 人团队、4 周（约 1 个月）周期，成员并行开发；每人每周须产出可审查的仓库产物。
2. **计算**：CPU 环境、无 GPU；Embedding 与 Reranker 均需在 CPU 上可运行。
3. **网络**：模型权重获取不稳定，须支持离线运行与本地模型目录优先解析。
4. **成本**：生成侧使用低成本/免费档模型，需容忍限流与重试。
5. **时间盒**：每周有固定验收节点（周五 Demo + Regression + 指标 + 技术总结），未达标项必须登记阻塞而非隐瞒。

**假设**

1. 手册为原生文本型 PDF，中文提取质量良好——**已实测成立**。
2. 印刷页 = 物理页 − 6（前 6 页封面/罗马数字前言不编号）——**已以页眉印刷数字逐页核对定值**，此前 +7/+6 记录均为方向错误，已作废。
3. 三级节是"能够独立回答一个典型开发者问题"的自然语义单元——**约 73% 的三级节落在 800–2500 字符的 embedding 舒适区**，假设基本成立。
4. HTML 开发指南的 Doxygen 结构稳定，可结构化解析——**已实测成立**（288 正文页，噪声过滤有效）。
5. 语料中存在"知识库确实无答案"的问题（如错误码 E1003 在语料中不存在）——**已实证**，且该类问题正是拒答能力的试金石。

## 2.14 本章小结

1. **需求本质**：本项目不是"做一个聊天机器人"，而是构建一条 **可核验的工程知识通道**——`正确知识 → 正确检索 → 有依据的回答`。因此**引文（Citation）与拒答（Abstention）是核心功能需求，而非增强项**。
2. **需求结构**：8 组功能需求（解析 → 单元化与元数据 → 检索 → 生成与引用 → 可靠性 → 服务化 → 评测平台 → 工程保障）＋ 14 条非功能需求，覆盖指南 §1、§5–§10、§13–§22 的全部要求项，并按 MoSCoW 与四周里程碑对齐。
3. **完成度**：截至第三周交付审查，**数据面与检索面已完整闭环**（1606 条统一 Node、三模式检索全通、1606 节点重建 24.8 min 红线内、266/266 单测通过）；**评测面为唯一主要缺口**，根源是 FR-7.2 期望来源标注不合格与 FR-7.5 回答质量 runner 未交付。
4. **风险核心**：项目最大风险不在生成模型质量，而在**知识工程质量与评测可信度**。R2（标注不可信）与 R3（指标量纲不可比）均已实际发生并被识别处置，其中"**宁可不出指标，也不出误导性指标**"（NFR-14）应作为本项目的方法学贡献写入结题报告。
5. **后续章节衔接**：第 3 章总体设计应围绕 §2.4 的 10 类场景与 §2.5 的 8 组功能需求展开；第 5 章测试与评价应直接以 §2.8 的评测需求与 §2.12 的未闭环清单为对照表，逐项给出达成与否的结论。
