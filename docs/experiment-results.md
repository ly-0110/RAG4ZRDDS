# ZRDDS 问答系统实验结果分析（2026-09-17）

> 本文件汇总四周全部实验的**正式数字**（口径与闸门见 §2），每张表的数字都可在
> `evaluation/reports/<实验名>.json` 中按题复核；复现命令见 §2.3。
> 数据源：《ZRDDS用户手册.pdf》（295 页）+ ZRDDS v2.4.0 Doxygen 开发文档（436 个 HTML），
> 统一 Node 集 **1638** 条（PDF 301 + HTML 1337）。

---

## 1. 结论速览

1. **分块方案**：结构感知分块是三种方案里最好的（hit@5 **0.7833**、mrr@5 **0.605**），
   纯语义切分在这套中文技术手册上明显最差（**0.2917 / 0.209**）——语义断点在"API 名 +
   参数表 + 错误码"这类内容上切得太碎。
2. **检索模式**（同一 struct 分块、同一 120 题）：向量 **0.7833 / 0.605**、BM25
   **0.6833 / 0.5393**、混合 RRF **0.75 / 0.6254**。命中率最高是向量，**MRR 最高是混合**
   ——融合把正确块排得更靠前（排位指标 +0.02）。
3. **多来源 + 精排**：跨来源 12 题上，`hybrid_rerank` 的 MRR **0.4792** 为全场最高
   （比 vector +0.10、比 hybrid +0.046），说明交叉编码器精排在跨来源题上有增量；
   版本加权（ver20/ver24）影响很小（±0.004）。
4. **回答侧**（final_v1，120 题）：faithfulness **0.8950**、answer_relevance **0.9883**、
   correctness **0.9633**、citation_accuracy **0.9583**（判分失败 0）；**24% 的题
   （29/120）走了拒答**。
5. **拒答专项**：20 题**全部不虚构**（16 题显式拒答 + 4 题"事实性否定 + 出处"），
   虚构风险 0。
6. **可复现与回归**：12 个实验回归矩阵 **12/12 pass**；报告带 Node/问题/标注**三指纹**，
   输入变了判 `incomparable` 而不是"退化"。

## 2. 评测口径与闸门（读数字前必看）

### 2.1 标注与闸门

检索指标的分母是 `evaluation/datasets/expected_sources.jsonl`（120 题真值标注）。
标注有效性由 `make audit` 把关（判据只来自 A 的产物与章节树，**不调用检索器**）：

| 检查项 | 现状 |
|---|---|
| 循环论证指纹（标注 = 检索 top-1 回显） | **0/120** |
| 题面有损转码（连续半角问号） | 0 处（历史 6 题已修） |
| 阻断项（页码越界 / 术语零命中 / 章页矛盾 / 实体全零命中…） | **0** |
| 判定 | **pass**（`make audit` 退出码 0；历史 44/120 → 48 题 → 4 题 → 0） |

两处口径在 2026-09-17 定版（此前是闸门红的根因）：

- **题面实体与标注页的关系**：只有当题面**全部**技术实体都远离标注页时才判"这页答不了这题"。
  双主题题（问 `on_data_available()` 又追问能否调 `create_datawriter()`）与"策略章节页 vs
  字段说明页"（标注 10.32 策略章节、字段说明在别处）都是合理标注形态 → 记非阻断留痕。
- **拒答专项合格口径**：合格 = 显式拒答 ∪ **事实性否定 + `[n]` 引用**（无出处的否定不算）。
  依据：模型对"有 `connect()` 吗"会直接否定并给出表号，这是比拒答更好的作答。

### 2.2 指标定义与可比性

- 检索：`hit_rate@5`（前 5 条里命中期望来源的题占比）、`mrr@5`（首个命中的倒数排名均值）、
  `precision@5`、`recall@5`（期望来源被召回的占比——多来源题有多个期望来源，故天然偏低）。
- 回答：`faithfulness`（答案是否有检索依据）、`answer_relevance`、`correctness`、
  `citation_accuracy`（引用是否张冠李戴/越界）。
- **跨实验不可比的情形**：不同问题集（120 题单来源 vs 12 题跨来源）、不同分块产物、
  不同来源集；报告用三指纹标记，回归器按此判 `incomparable`。
- `score` 量纲随检索模式变（cosine / 原始 BM25 / RRF≈0.03 / 精排 sigmoid），**跨模式不可比**。

### 2.3 复现命令

```bash
make ingest                      # 或 python scripts/ingest.py --config <cfg> 重生产物
make index     CFG=configs/experiments/<实验>.yaml
make experiment CFG=configs/experiments/<实验>.yaml    # 检索（+回答侧，若配置了）
make regression                                         # 全量矩阵比对
make audit                                              # 标注闸门（指标通道前置）
```

## 3. 检索侧结果

### 3.1 分块方案对比（向量检索，120 题）

| 实验 | 分块 | 块数 | hit@5 | mrr@5 | precision@5 | recall@5 |
|---|---|---|---|---|---|---|
| `struct_v1` | 结构感知（三级节为单元，超长沿子节下切） | 301 | **0.7833** | **0.6050** | **0.1733** | **0.7833** |
| `hybrid_v1` | 结构 + 语义（超阈值节语义二次切分） | 906 | 0.5500 | 0.3419 | 0.1633 | 0.5500 |
| `semantic_v1` | 纯语义（SemanticSplitter，按相似度断句） | 622 | 0.2917 | 0.2090 | 0.0783 | 0.2917 |

**解读**：结构感知分块在本语料上领先幅度很大（hit@5 高 23pp，mrr 高 0.26）。
语义切分的问题不是"方法不好"，而是**中文技术文档的语义断点与知识边界不一致**：
函数名、参数表、错误码会被切成碎片（该方案曾出现 166/1059 块 <50 字符，加最短长度过滤后
仍碎片偏多），检索命中后再好的排序也救不回定位错误。混合方案居中——
它把超长节交给语义切分，但被切碎的那部分同样吃亏。

> 结论落地：**主推 struct_v1**；`semantic_v1` / `hybrid_v1` 作为对照保留在矩阵中。

### 3.2 检索模式对比（同一 struct 分块，120 题）

| 实验 | 模式 | hit@5 | mrr@5 | precision@5 | recall@5 |
|---|---|---|---|---|---|
| `struct_v1` | vector（bge-m3 + chroma，cosine） | **0.7833** | 0.6050 | **0.1733** | **0.7833** |
| `struct_hybrid` | hybrid（vector + BM25，RRF k=60，引用制零重建） | 0.7500 | **0.6254** | 0.1617 | 0.7500 |
| `struct_bm25` | bm25（字符 bigram + ASCII 词整体保留） | 0.6833 | 0.5393 | 0.1450 | 0.6833 |

**解读**：三者差距不大（hit@5 区间 0.68~0.78），但**排序质量**上混合最好（mrr@5 0.6254，
比向量高 0.02）——RRF 让"两路都命中的块"排到更前。BM25 单用略低但在**精确 token 题**
（错误码、API 名、`v2.4` 这类）上是必要补充，且建库只要 0.1s（向量 301 节点约 8 分钟）。

> 结论落地：默认沿用 `struct_v1`（速度/命中率最好）；需要排序质量或精确 token 场景时
> 用 `struct_hybrid`（引用既有子索引，**零重建**、无额外索引成本）。

### 3.3 多来源（PDF + HTML 统一 Node 集）与精排

跨来源问题集 `questions_multisource.jsonl`（12 题，25 条期望来源；覆盖"HTML 更适合回答"
与"两来源联合回答"两类场景）：

| 实验 | 模式 | hit@5 | mrr@5 | precision@5 | recall@5 | 耗时 |
|---|---|---|---|---|---|---|
| `struct_multisrc_v1` | vector | 0.5833 | 0.3778 | **0.1667** | 0.2778 | 9.5s |
| `struct_multisrc_bm25` | bm25 | 0.2500 | 0.2500 | 0.0500 | 0.1111 | 0.2s |
| `struct_multisrc_hybrid` | hybrid | 0.5833 | 0.4333 | **0.1667** | **0.3194** | 10.0s |
| `struct_multisrc_hybrid_ver20` | hybrid + 版本偏好 2.0 | 0.5833 | 0.4375 | **0.1667** | **0.3194** | 9.8s |
| `struct_multisrc_hybrid_ver24` | hybrid + 版本偏好 2.4 | 0.5000 | 0.3611 | 0.1500 | 0.2778 | 9.9s |
| `struct_multisrc_hybrid_rerank` | **hybrid + 交叉编码器精排** | 0.5833 | **0.4792** | 0.1500 | **0.3194** | 206.2s |

**解读**：

- **精排是唯一在跨来源题上明确改善排序的手段**（mrr@5 0.4792，比 hybrid 高 0.046、
  比 vector 高 0.10），代价是单题从 ~0.8s 涨到 ~17s（CPU 精排 30 候选）。
- **BM25 在跨来源题上明显弱**（hit@5 0.25）：跨来源题多用自然语言问"HTML 示例里怎么做"，
  词面重叠少；这也印证了向量/融合在该场景的必要性。
- **版本加权影响很小**（±0.004）：当前语料只有手册 2.0 与 HTML 2.4 两个版本，且
  "偏好 2.4"只在同时命中两来源时改变排序，可操作空间本来就小。
- `recall@5` 在这里只有 0.28~0.32：**多来源题期望同时命中多个来源**，前 5 条装不下，
  这是口径使然，不是检索崩了（hit@5 与 precision@5 才是这个集上的主指标）。

### 3.4 跨来源能力（定性）

`struct_multisrc_*` 在同一个 Node 集里同时含 PDF 与 HTML 节点，实测典型形态：
`DDS_Publisher_create_datawriter` 这类 API 题 top-1 命中 HTML 的 API 页、top-2 命中
手册对应章节（双来源共存）；引用卡按来源分型渲染（PDF 报双页码，HTML 报原文链接）。
冲突/版本类问题上，Prompt v2 的"来源优先级 + 冲突披露"规则会主动说明两来源差异
（例：C API 与 C++ 接口的差异）。

## 4. 回答侧结果（final_v1 · 120 题终跑）

配置：`final_v1.yaml`（struct 分块 + 向量检索 + Prompt **v2** + `source_priority=[zdrds_dev_guide, user_manual]`），
索引与 `struct_multisrc_v1` 共用（`d57f695e`，零重建）。生成模型本机 Ollama `qwen3.5-9b`（经 `models/llm_gateway.py`）。

| 指标 | 均值 | n | 判分失败 |
|---|---|---|---|
| faithfulness（答案是否有检索依据） | **0.8950** | 120 | 0 |
| answer_relevance | **0.9883** | 120 | 0 |
| correctness | **0.9633** | 120 | 0 |
| citation_accuracy | **0.9583** | 120 | 0 |
| 拒答 | **29 / 120（24%）** | — | — |

- 检索阶段 **30.4s**（120 题 / 1638 节点）；回答侧墙钟 **≈84 分钟**（≈42s/题：
  逐题生成 + 4 次判分，本地 9B）。
- faithfulness 是四项里最低的（0.895）：约 10% 的答案被判"有超出检索依据的表述"，
  这是最值得继续压的指标（Prompt 迭代 / 更强 judge 模型 / 上下文裁剪）。
- 24% 的拒答率与"问题集含 10 题**不存在信息**类+若干越界题"的设计相符；拒答专项（§5）
  验证了这些拒答**不是**因为检索给不出东西而摆烂，而是有依据的边界表达。

## 5. 拒答专项（20 题"不存在信息"）

题集五类：杜撰 API 4 / 杜撰错误码 3 / 杜撰功能 7 / 跨版本断言 3 / 越界 3。

| 归类 | 题数 | 说明 |
|---|---|---|
| 显式拒答（"当前知识库无法确认"） | **16** | 直接用拒答措辞 |
| 事实性否定 + `[n]` 引用 | **4** | 例：AB-001 答"ZRDDS 的 DomainParticipant **没有提供** `connect()` 方法"并列出表 6-2 可用函数；AB-004 指出恢复暂停分发的实际函数是 `DDS_Publisher_resume_publications` 而非 `resume()` |
| **虚构风险（confident）** | **0** | — |

**结论：20/20 全部不虚构**（`generation.abstention.classify_answer` 判定；
原始 20 条答案在 `evaluation/reports/abstention_eval.json` 逐题可查）。
按新口径重判后闸门退出码 0，可直接挂 CI。**仍需人工签署**：`evaluation/reports/manual_review.md`
的 30 题六问清单（含 4 题口径题）待评审人逐题签字。

`evaluation/datasets/error_cases_real.jsonl`，全部源自真实实验报告与人工审计真值

|---|---|---|

这 40 例"已验证脱靶"是分块与检索改进的**回归靶子**：修复前后跑同一批题即可验证是否真的改善，

## 7. 数据层修复对结果的影响（H1）

用户报障发现 HTML 加载器在"直系正文 + 标签子元素混排"时丢弃直系文本（`n<sub>i</sub>`
下标碎片化的根因）。修复后重生成产物：

| 项 | 修复前 | 修复后 |
|---|---|---|
| HTML 正文字符 | 733,172 | **781,442（+48,270，+6.6%）** |
| HTML 节点 | 1305 | 1337 |
| 重复节点 | 94 | 63 |
| 统一多来源 Node 集 | 1606 | **1638** |
| PDF 侧产物 | — | 301 块**逐字节不变**（指纹 `adcca4de72d4`） |

**索引影响核查结论：零重建**——13 个配置的身份哈希未变、6 套索引的 manifest 产物指纹与
当前产物逐一 MATCH、无孤儿目录；只有 HTML 侧产物变化的那两套多来源索引按预期重建
（bm25 0.1s / vector ≈25min）。

## 8. 回归与可复现性

- **回归矩阵（`make regression`）**：12 个实验 **12/12 pass**，且**指标通道已开启**
  （`--with-metrics`，标注闸门已 pass）；明细通道同时核对 top-K 重合率 ≥0.8、rank-1 一致率、
  返回条数与耗时。
- **回答侧实验默认不重跑**：`response_metrics` 非空的配置（`final_v1`）一次要 ≈84 分钟
  （120 题逐题生成 + 四次判分），回归默认只比对它的既有报告，需要重跑时显式加
  `--with-response`——避免一条 `make regression` 意外挂两小时（2026-09-17 加的守卫）。
- **三指纹可比性闸门**：报告携带 Node 集 / 问题集 / 标注集指纹。本次因 H1 产物重生成、
  标注收窄、多来源数据集接线，多来源组一度判 `incomparable`（设计使然，不是退化）；
  重跑 + `--promote` 重锚后全部归位 pass。
- **一键链路**：全新 `.venv` 走 `make setup` 安装成功 → 新 venv 内 `pytest tests/` **448 例全绿**、
  `make ingest` 产物与 Git 版本零差异（"三行命令可跑"闭环）。
- **索引成本**：struct 301 节点 ≈7.8min、semantic（622 节点）≈8.8min、hybrid 906 节点 ≈19.6min、
  多来源 1638 节点 ≈25min——红线（≤30min）内；索引身份只取 chunking/embedding/index/retrieval
  四段，改生成或评测配置**不触发重建**（本轮实测 13 个配置全部复用既有索引）。

## 9. 局限与后续

| 局限 | 说明与建议 |
|---|---|
| 跨来源题集只有 12 题 | 单题 = 8.3pp，结论方向可信、细粒度差异（如版本加权 ±0.004）不宜当定论；建议扩到 30~50 题 |
| judge 用本地 9B 模型 | faithfulness 等分数的绝对水平受判分模型影响；建议用同一 judge 模型做**纵向对比**（配置间比），不要与外部论文数字横比 |
| 精排成本 | 单题 16s（CPU，30 候选）；若上演示需预热，若上生产建议换小模型或降 `candidate_top_k` |
| semantic/hybrid 分块的碎块 | 已加最短长度过滤（<50 字符块 166→50），仍建议后续做"API 名/错误码保护"的切分规则 |
| 未验证项 | 容器化（本机无 Docker）、人工抽检 30 题签署、MCP 宿主端演示 |
